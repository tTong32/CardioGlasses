1. What We Are Building

One sentence: Glasses with a pulse sensor and motion sensor that watch a heart patient's body all day, compare it to that person's normal and medical history, and speak up only when it matters.

The problem (KNOW): People with heart disease are monitored only at clinic visits. At home, changes go unnoticed. Wearables show raw numbers (heart rate) but don't say "is this unusual for me, given what I'm doing and my history, and should I act?"

The user (KNOW): An older adult with existing cardiovascular disease or high risk.

  • Environment: home, daily life, exercise, recovery.
  • Does manually today: checks pulse or an app, guesses whether a number is worrying.
  • Doesn't know: whether a change is normal for them, whether it's persistent, or what to do.
  • Why useful: "We'll tell you when your data matters" — no screen-watching.

The solution: Glasses stream pulse (PPG) and motion (IMU). Software works out heart rate, whether the person is resting or moving, and whether the signal is trustworthy. It compares that to the person's baseline and clinical record (FinchNode), decides normal / monitor / notify / escalate, then speaks a short ElevenLabs message and shows the full explanation on the phone.

Measured: heart rate, beat timing, motion, signal quality. Inferred: concern level (never "heart attack").
Not a medical device: wording is "guidance / check in", never a diagnosis.

5. Contracts Between Components

Agree in Hour 0–1. Don't change without telling everyone. Time = Unix ms.

A — Hardware → AI (one JSON line per sample over USB serial, ~50 Hz; same columns in replay CSV)

{"t": 1760000000123, "ppg": 51234, "ax": 0.02, "ay": -0.98, "az": 0.10, "gx": 0.5, "gy": 0.1, "gz": 0.0}

(PPG raw only for MVP. 2nd PPG channel optional. OPEN D-06: raw vs features — default raw.)

B — AI → Software (Reading, every ~2 s)

{"t": 1760000002000, "hr": 78, "ibi_ms": [790, 772, 765], "activity": "resting|moving",
 "quality": 0.91, "baseline_hr": 68, "deviation": 1.8, "persist_s": 45}

C — AI → Software (Alert, only on state change)

{"t": 1760000050000, "level": "normal|monitor|notify|escalate", "confidence": 0.8,
 "headline": "Elevated heart rate at rest", "reason": "…compared with your baseline and history…",
 "voice_text": "Your heart rate has stayed high while you're resting. Please sit down and check your phone.",
 "next_step": "Sit down and review", "reading": { … }}

D — Software → AI (PatientContext, loaded at start)

{"patient_id": "demo-1", "age": 71, "conditions": ["…"], "medications": ["…"], "risk_tier": "high",
 "config": {"min_quality": 0.6, "persist_s": 30, "deviation_trigger": 2.0, "cooldown_s": 120}}

Rules: unknown/missing values = null, never omitted · levels are exactly those four strings · low quality → no alert, quality reported honestly.

6. Implementation Workflow (one event, start to finish)

sequenceDiagram
  participant G as Glasses
  participant SP as Signal processing
  participant B as Backend
  participant F as FinchNode
  participant DL as Decision
  participant V as ElevenLabs
  participant UI as Phone
  B->>F: fetch patient (startup)
  F-->>B: PatientContext
  G->>SP: raw PPG + IMU
  SP->>B: Reading (HR, activity, quality)
  B->>DL: Reading + baseline + context
  DL-->>B: Alert (notify + reason)
  B->>V: voice_text
  V-->>B: audio
  B->>UI: Alert + live data (websocket)
  Note over G,UI: Patient rests, HR normalizes → level returns to normal → monitoring continues
  1. Backend starts, pulls the synthetic patient from FinchNode, builds PatientContext.
  2. Glasses stream raw PPG + IMU to the laptop (or replay player does).
  3. Signal processing filters PPG, finds beats → HR + beat intervals; IMU → resting/moving; scores quality.
  4. Every ~2 s a Reading is sent to the backend and stored.
  5. First 60 s at rest = calibration: sets baseline_hr.
  6. Decision gate: quality ≥ threshold AND resting AND deviation persists → run reasoning step. Otherwise normal/monitor.
  7. LLM (given reading, baseline, conditions) writes reason + voice_text, picking only from the four levels.
  8. Backend sends text to ElevenLabs → audio plays; same alert pushed to dashboard.
  9. Monitoring never stops; when readings return to baseline the state drops back to normal.

11. If Everything Goes Wrong

Rule: at Hour 18 (or with 4–6 h left) with half the system broken, cut to this.

Keep (the core idea): a data stream (replay or finger-on-sensor) → HR + activity + quality → baseline → FinchNode context → decision with a plain-English reason → voice + dashboard card → recovery.

Cut, in this order Replace with
1. Everything in Optional + Should —
2. Live glasses placement Sensor on finger/wrist, glasses just mounted for show; or recorded real data via replay
3. LLM reasoning Templated reason strings from rules (keep context fields in text)
4. Postgres/Tiger Data SQLite or in-memory
5. FinchNode live call Cached/hardcoded patient JSON (keep FinchNode if it ever worked)
6. Live ElevenLabs Pre-generated audio clips
Never cut Activity-aware + baseline-aware decision, voice + "why" card, recovery to normal
